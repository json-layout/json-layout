# Baseline — 2026-10-29, the form tools against a plain JSON API

The first run of the same cases under three tool surfaces (spec:
`docs/superpowers/specs/2026-10-28-webmcp-eval-plain-json-arm-design.md`):

- **form** — the page's form tools (`describeState`, `setFieldValue`, `setData`, `editArray`,
  `getFieldSuggestions`, `getData`) and the form guide;
- **session** — the same tools through `@json-layout/agents`' `FormSession`, plus `saveForm`;
- **plain** — what a JSON API offers: `readDocument`, `readSchema` (raw schema, vendor keywords
  included), `writeDocument`, `patchDocument` (JSON merge patch), `httpGet` against the same
  base the form's `getItems` uses. Every write is validated by ajv and refused as a 400 would
  be; layout rules (`x-if`, `getItems`) are not enforced. Its prompt is the goal, a neutral API
  description and the schema's `x-agent-guide`.

## Setup

- Model `haiku` (served as `claude-haiku-5-5`), 3 runs per case per arm, code at `069705d`.
- Cases: `data-fair-line` (a 15-column record from a forwarded email, a commune referential
  served offline with homonyms), `calendar` (dependent picker + `x-if` section, live
  koumoul.com), `portal-config-edit` and `charts-edit` (a populated document, a small change,
  a check that nothing else moved), `contact` (control).
- **Not runnable**: the session arm on `calendar`, `charts-edit` and `portal-config-edit`.
  These are application configurations, auto-saved in production, and `FormSession` has no
  auto-save mode yet; the arm reports that instead of faking it (9 of the 45 planned runs).
- 36 runs, 33 judged (the 9 not-runnable have no transcript). One judge per run, reading the
  evidence file and the arm's tool set.
- **Caveat: the checks were visible to the judges.** The evidence file carries the `checks`
  results beside the calls; the judges were told to ignore them, but the spec wants the judge
  blind to checks. Follow-up: keep checks out of the judged transcript.
- **Caveat: the largest responses did not reach the model whole.** Token accounting says so
  for both arms on `portal-config-edit`: the plain arm's `readSchema` answered 128,651 bytes
  and the form arm's root `describeState` 61,968 bytes, yet the *whole* runs wrote only
  15.9–16.8k (plain) and 11.1–13.9k (form) tokens to the cache, system prompt included —
  less than either response alone. Claude Code shortens large MCP results before the model
  sees them (mechanism not confirmed here; the agent has no file tools to read a spill-over).
  The `bytes` column is what the servers answered, not what the model read. The `charts-edit`
  `readSchema` (29,454 bytes) fits its run's cache writes and appears to have arrived whole.

Files: `<case>[--arm].r<n>.json` (evidence: calls, responses, final data, checks),
`.run.json` (runner sidecar: model, cost, tokens, answer), `.verdict.json`, and `report.txt`
(the printed `webmcp-eval:report`). The as-seen schemas (`*.schema.json`) are not kept: they are
regenerated by a run.

## Findings per claim

The five reasons of `core/src/webmcp/README.md`, "Why not just hand the model the schema".

**1. Branches that do not apply until chosen.** Not a differentiator here. `calendar`'s
`crowdSourcing` sits behind `x-if: datasets.0.isRest`: the plain arm wrote it together with
`isRest: true` in all three runs (r1 #6, r2 #9, r3 #5). `portal-config-edit` adds a menu item
from a discriminated `oneOf`: the plain arm read `/$defs/menuItem` (#6) and wrote a valid
`{type: "generic", pageRef}` in one patch, 3/3; the form arm needed `editArray` + a variant
switch + suggestions. `charts-edit`'s five-level `oneOf` was already chosen in the starting
document: a data-path merge patch needed no branch knowledge, while the form arm had to write
at `/$allOf-1/chart/$oneOf/1/config/$oneOf/2/valueCalc/$oneOf/1/metric` (one run, r3 #2–#3,
dropped the `$` and lost two calls). No case asked for a branch the document did not already
make obvious.

**2. Accepted values not in the schema.** Refuted as stated ("nothing else can"). With the
`getItems` URL templates visible in the raw schema, the plain arm built the lookups itself in
9/9 runs: `communes?q=…` (data-fair-line #3), the dataset listing and
`…/schema?calculated=false` (calendar r1 #4–#5, r2 #3 and #6), the `context` resource for
portal pages (#3). Same referential, same homonyms: both arms saw the three "Saint-Sébastien"
communes and picked 44190; no arm invented a code. The form arm's suggestion memory cost calls
instead (see open findings).

**3. Values far larger than the answer.** Partly. The form stored the 12,508-character
dataset object by suggestion index, untouched by the agent. The plain arm did not need to
reproduce it to pass the API: r1 and r3 wrote a three-key reference (`href`, `title`,
`isRest`), which the schema accepts. r2 did copy the dataset with its 37-column schema
(#10, a 14 KB patch) and became the suite's most expensive run (11.5k output tokens, $0.014).
The plain documents differ from what the form stores (dataset without `schema`, `labelField`
as the whole column in r1, five keys in r2, `{key, label}` in r3); whether the calendar
application renders from them is not checked by these runs.

**4. A schema bigger than the conversation.** Measured on `portal-config-edit` only (128 KB
raw schema; `portal-page` was not run). Outcome tie, 3/3 each; calls 9 vs 10–12; input tokens
tie (84–87k vs 78–91k); bytes answered double on the plain side. But see the caveat above:
neither arm's big response reached the model whole, and the plain agent worked from the
`x-agent-guide` in its prompt plus pointer reads (`/properties/menu`, `/$defs/menuItem`,
`/properties/theme/properties/assistedModeColors`). The "forty times the interaction" figure
was not reproduced, because the client did not let the schema into the conversation.

**5. A live form, errors scoped to the change.** Mixed. For the form: the scoped answers did
guide recovery (`charts-edit` r3 not-found lists the real roots; `calendar` "No option matched"
r2 #5; "N field(s) became available" after each branch-opening write). Against it: on
`data-fair-line` the per-field write path is what made the form arms long — the SIRET is
refused as a number and quoting it makes it worse (below). For the plain arm: one whole-document
400 was enough to fix a type (`/labelField must be object`, calendar r2 #5), but a write that
cut `datasets[0].schema` to one column was accepted (calendar r2 #9): ajv validates the type,
not coherence with the remote listing; the agent caught it itself (#10).

## Not among the five reasons

- **On a flat record from loose text, the plain arm wins clearly.** `data-fair-line`: read the
  schema, one lookup, one `writeDocument` — 4 calls, 3/3. The form arm wrote field by field
  (15–18 calls) although the goal held every value; the session arm r1 used one `setData` and
  still needed 8.
- **Digits for a text field.** In all six form/session runs, the first SIRET write reached the
  server as a JSON number (`"value": 52348761900017`, form #8, session r2 #8, r3 #10), refused
  with "must be string"; the next attempt sent literal quotes (`"\"52348761900017\""`, form #10
  r1/r3, #11 r2; session r2 #10, r3 #14), refused by the pattern; only a `setData` with a string
  fixed it (form #14 r1/r3, #17 r2; session r2 #15, r3 #17). The plain arm sent a string inside
  its document every time.
- **Suggestions dropped after a write.** Session r1: a `setData` that did not touch `/commune`
  (#3) dropped the memorised commune list, and `suggestionIndex` failed (#4: "dropped by a
  write that may have changed this field's options"); two more calls to recover.
- **Multi-valued selects look single-valued.** `describeState` shows `/activites (select,
  values=[…])` with nothing saying it holds a list; session r2 #12–#13 and r3 #11–#12 wrote a
  scalar and got "must be array". The form runs happened to send arrays first.
- **The plain arm reads more for small edits.** `charts-edit`: a 29 KB `readSchema` (#2) for a
  two-field change; form arm 8.2 KB `describeState`. The only case where the form arm is
  repeatedly and markedly cheaper.

## Open findings per arm

Anchored to the evidence file's call numbers (1-based). Judges' own call numbers are off by one
in `data-fair-line--session.r3` and `charts-edit.r3`; the anchors below are the transcript's.

**form / session**

- `setFieldValue` refuses a 14-digit number for a `pattern=^\d{14}$` text field and its error
  does not suggest sending a string; the agent's quoted retry stores the quotes
  (data-fair-line r1 #8/#10, r2 #8/#11/#14, r3 #8/#10; session r2 #8/#10, r3 #10/#14). Medium.
- Memorised suggestions dropped by a `setData` that did not touch the field
  (data-fair-line--session r1 #3→#4). Medium.
- A multi-valued select is not marked as an array in `describeState`
  (data-fair-line--session r2 #12–#13, r3 #11–#12). Medium.
- `getFieldSuggestions` at a data path that skips the active variant segment answers and
  memorises under that path; `setFieldValue` at the full path then finds nothing memorised
  (portal-config-edit r2 #7→#8, recovered at #11–#12). Medium.
- The not-found error for `/menu/children/2/$oneOf/pageRef` lists the top-level tabs, not the
  variant segment the path lacks (portal-config-edit r1 #7, r3 #7). Low.
- A suggestion of an object value renders as `([object Object])` (portal-config-edit r1 #8,
  r2 #7/#11, r3 #8). Low; already open since `2026-10-02-portal-config`.
- Extra reads that bought nothing: a closed list re-listed by `getFieldSuggestions`
  (data-fair-line--session r3 #3), redundant `describeState` (data-fair-line r2 #12–#13,
  calendar r3 #4–#5, portal-config-edit r3 #10), an optional field explored (calendar r1 #9,
  r2 #10). Low.

**plain**

- A write accepted although `datasets[0].schema` no longer matched the listing
  (calendar r2 #9). Medium: the API arm has no coherence check beyond the schema.
- `/labelField must be object` gives the type, not the expected shape (calendar r2 #5); and
  three runs stored three different `labelField` shapes with nothing saying which the
  application needs (calendar r1 #6, r2 #10, r3 #5). Medium / low.
- `readSchema` without a path returns the whole schema (portal-config-edit #2, 128 KB;
  charts-edit #2, 29 KB) and the agent re-reads by pointer afterwards. Low.
- A merge patch cannot append: the whole `menu.children` array is resent
  (portal-config-edit #7). Low; correct in all three runs.
- Nothing in the write's answer confirms derived values (the portal palettes the
  `x-agent-guide` says are recomputed on save) (portal-config-edit #7). Low.
- The commune homonyms are disambiguated from outside knowledge in both arms
  (data-fair-line--plain r1 #3; form and session #2 show the same three). Low; a property of
  the fixture, which is the point of it.
